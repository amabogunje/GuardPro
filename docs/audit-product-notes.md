# Independent product and commercial launch review

Reviewed 16 September 2026. Read-only application review; no production data changed. This is an independent challenge to readiness, not a new feature wishlist. Evidence is current source; deployment configuration statements in documents are not a live cloud audit.

## Minimum product that can be sold

A small, assisted-onboarding paid pilot: an owner contracts with ISDL, an operator provisions the customer/property/owner, the customer supervisor configures named guards, daily shifts, checkpoint routes and instructions, guards capture attendance/patrols/problems, supervisors review exceptions and close problems, and the owner sees an honest summary and can inspect evidence. Collect setup/monthly charges by manual invoice and record payment in an operator ledger. No payment gateway, AI, chat, continuous GPS or emergency dispatch is necessary. Sell recorded supervision, not guaranteed security or live monitoring. Cap pilot sites/users and supported Android/browser versions until capacity and device results exist.

The current application is a substantial demo, not yet an independently evidenced production service. Guard/supervisor polish cannot substitute for reliable synchronization, accurate expectations, account recovery and deploy isolation. Owner has additional acquisition/onboarding and interpretation gaps.

## Guard experience

Primary job: record work and problems with little effort, with confidence the evidence was saved. Secondary: understand the assigned shift and recover from connectivity/device interruptions without unfair blame.

* Must before paid use: remove the prominent nonfunctional Emergency action or replace it with a real telephone action labelled as such. `public/app.js:628` renders the red action and `public/app.js:1747` opens an explicit not-implemented dialog. Emergency delivery itself is intentionally outside MVP; an inert emergency affordance is not a viable operational control.
* Must: demonstrate production-phone recording, QR, denied permissions, foreground offline retry, lost connectivity and full storage. `docs/VERCEL.md:52` explicitly leaves device testing outstanding. This is evidence work, not a demand to build native background execution.
* Must: operational account/password recovery that preserves recoverable pending work. Password changes update the account and revoke sessions (`server.js:1419-1423`) but documentation says old-password local work must be recovered first (`README.md`, Supervisor settings; `docs/OPERATIONS.md`, password loss). Acceptance: a planned reset with pending audio/photo does not silently strand evidence; unexpected loss has a documented escalation and honest loss warning.
* Defer: voice AI, chat, achievements/promotion scores, continuous GPS, remote browser wipe, automated police contact.

## Supervisor experience

Primary job: know what requires intervention and act quickly. Secondary: demonstrate coverage and responses using defensible records.

* Must: make attendance represent the selected shift occurrence. `public/supervisor-status.js:75-86` counts any overlapping shift. Executable fixture: guard starts yesterday 06:00, never ends; selected shift is today 06:00–18:00, now noon. KPI returns `1 of 1`, `tone: good` without today's check-in. Add overdue-shift reconciliation and ensure old open shifts do not satisfy a new attendance obligation. Acceptance: legitimate overnight shifts work; stale prior shifts produce an explicit exception, not good coverage.
* Must: historical completion use the recorded route/schedule snapshot. `public/supervisor-status.js:116-123` and `:189-196` compare scans against the current checkpoints argument. Adding or retiring a checkpoint can change apparent completion of a past patrol. Acceptance: saved completed patrol remains completed after route edits; future patrol uses the new route.
* Must: agree and test one attendance/patrol denominator across owner health, supervisor KPI and downloaded reports. Owner patrol health measures start events; supervisor KPI measures checkpoint completion. These are valid different measures only if labelled distinctly and never equated. Named versus Any guard expectations also differ intentionally; Any cannot demonstrate required staffing.
* Must: define a phone/WhatsApp escalation and daily review responsibility outside the application; in-app messaging is deliberately disabled. Do not require new chat/notification infrastructure to sell an explicitly monitored-by-customer pilot.
* Defer: repair work orders, multistage acknowledgement/assignment, task management, AI summaries, supervisor-to-guard chat, complex workforce scheduling unless first pilot rosters require it.

## Owner experience

Primary job: confidence that agreed supervision is taking place, knowing when confidence is limited. Secondary: establish properties/responsibility, access supporting evidence, and act as supervisor when needed.

1. **Provision a real first customer/property (must).** `public/owner.js:13` offers Add your property when none exists. `public/property-location.js:38-40` submits `additional_site` using existing `site.id`; `server.js:1365-1382` obtains customer from that existing site and requires its assignment. `server.js:1356-1357` rejects customer creation. `migrations/001.sql:2-5` models owner through assignments, with no owner/customer membership. Acceptance: a real new customer receives an individual owner account and first property without demo access or ad-hoc SQL; second property remains isolated. An audited operator provisioning command is sufficient for paid pilot. Self-service signup/zero-property creation is required only if advertised.
2. **Treat owner-as-supervisor as configured (must for that launch variant).** Owner is offered Act as supervisor (`public/owner.js:29-30`), but setup complete checks only assigned supervisor users (`owner-overview.js:31`), so owner-only supervision remains unfinished. Persist responsibility choice; acceptance: owner-only configuration completes setup and retains actual owner attribution.
3. **Surface uncertainty, not just timestamp (must).** Freshness computation already distinguishes capture and receipt (`owner-overview.js:22-35`); home displays receipt only (`public/owner.js:18`). New receipt of an old offline record can look reassuring. Acceptance: stale/unknown coverage explicitly says current activity unconfirmed even when latest receipt is recent. No need for a large new dashboard.
4. **Make score meaning defensible (must).** `owner-health.js:11` measures seven completed calendar days, excluding today; `:39-43` measures patrol starts, not complete rounds. Display label is only Last seven days (`public/owner-health-view.js:9`). A start with zero scans can still earn full patrol health. Keep an unambiguous start-timeliness label, or calculate completion health as the owner-facing measure. Add clear reporting cut-off (for example through yesterday) and evidence freshness. Score formula is a chosen heuristic, not validated security probability.
5. **Handle incomplete classification without reassurance (must).** Classification happens at resolution (`server.js:1069` onward); unresolved security issues can remain unknown. `owner-health.js` risk has all-report denominator and unclassified count; retain that disclosure. Acceptance: unresolved/unclassified reports cannot be communicated as low risk; P1 definitions and report percentage denominator are explained. Existing resolved unclassified rows need either explicit unknown or a controlled supervisor reclassification path. Backfill guesses are unacceptable.
6. **Read-only evidence access (must or explicit support channel).** KPI cards intentionally are display-only (`public/owner-health-view.js:6-9`) and owner actions offer only Property/Supervisors/Subscription (`public/owner.js:10`). Owner can switch to supervisor, but evidence viewing should not require a management mode. A single read-only Reports/Problems link is enough; expansive clickable KPI analysis is not required.
7. **Manual subscription sufficient (must operationally, not automated).** `public/owner.js:34` honestly says billing unconfigured. For a paid pilot, contract, invoice, service dates, payment ledger and support contact are sufficient. Either replace that screen with accurate manual-service contact/status or hide it. Automated billing, renewals and payment processing can wait.
8. **Address confirmation needs assisted validation (pilot procedure).** `public/property-location.js:3-14` requires coordinates and external map lookup. For a low-touch launch improve map selection later; for pilot have operator verify the physical position/radius with owner. Acceptance: wrong-address/poor-GPS cases cannot create confident absence allegations.

## Cross-role launch dependencies

* Isolate customer production from demo and preview databases/media. `docs/VERCEL.md:48-50` documents public shared demo credentials and a shared preview/production demo schema. Verify actual cloud state before claiming fixed.
* Supply usable account recovery, backup+media restore, loss/revocation, retention/export/offboarding and support runbooks; execute at least one restore and offboarding rehearsal. `docs/OPERATIONS.md` currently describes manual decisions/procedures rather than demonstrated automation. Automation can wait, operational accountability cannot.
* Reconcile obsolete docs/tests with shipped scope: README demo still mentions acknowledgement, handover, AI approvals; `docs/PILOT.md` still tests urgent delivery and assignment workflows removed from current MVP. Passing old tests or failing them as obsolete cannot serve as a release gate. Maintain a current critical-path suite plus a real-device acceptance record.
* Confirm commercial hosting allowance, spending caps, support owner and incident response without buying services as part of this audit. `docs/VERCEL.md:54-58` documents an existing Hobby team and plan verification remaining; needs current verification, not an assumption.

## Exit gate

Do not classify roles independently as production-ready until the shared service gate passes. Run one full named-roster week with real approved phones, including overnight shift, missed check-in, late patrol, offline audio/photo, password/session expiry, lost-device exercise, problem resolution/classification, owner review and export. All expected denominators and history must reconcile. Two isolated test customers must not access one another's records/media. Restore database and media together, and provision/offboard a fresh customer using the supported procedure. Success qualifies a bounded paid pilot; scaling and self-service acquisition require separate evidence.
