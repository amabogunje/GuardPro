# Architecture and pilot boundaries

## Components

- `server.js`: Express HTTP API, sessions, authorization, SQLite queries, private media, QR generation and notifications.
- `ai.js`: replaceable server-side transcription and narrative adapter. No browser secrets.
- `migrations/`: relational schema, foreign keys and a partial unique index preventing concurrent active shifts for one guard.
- `public/app.js`: guard, owner and supervisor screens. Plain JavaScript and CSS, with no build step or third-party browser scripts.
- `public/vault.js`: IndexedDB vault, PBKDF2-SHA256 (250,000 iterations) and AES-GCM with random salt/IV. Writes are serialized; passwords are never persisted. A temporary unlock key is kept in tab-scoped sessionStorage to support refresh.
- `public/sw.js`: essential public app-shell caching. API and private media responses are never service-worker cached.
- `tests/workflows.test.js`: API integration and real Chromium browser automation.

SQLite and filesystem media keep local operation inexpensive and understandable. This is one server on one persistent volume, not a horizontally scalable service. Node's built-in SQLite API may emit its experimental warning. Move to PostgreSQL and private object storage when workload, isolation or durability requirements justify that work. Do not run this database on a network filesystem for a real pilot; the current development workspace happens to be in OneDrive, so configure a non-synced data location before operational use.

## Data and permissions

Customers own sites. Every user has explicit site assignments; role names do not grant global access. Supervisors only administer assigned sites and can create customers for themselves to manage. Owners are read-only. Guards only write their own records and access assigned-site instructions, their shifts, their reports and relevant unresolved handover issues. End-shift notes are shared within the assigned site. Every protected write checks role and site server-side. All SQL parameters supplied by users are bound.

Passwords use salted scrypt. Sessions last 12 hours, use HttpOnly SameSite=Strict cookies, and API calls also require a session proof unlocked from the encrypted vault. Cookie alone cannot read the API after an offline app sign-out. Private media links are signed, user-bound and expire after two minutes, and still require an authorized session. Restarting the server invalidates outstanding media signatures. Previously issued links remain usable until expiration, as with most signed-link systems; signing out online revokes the session immediately.

Record IDs are device-generated UUIDs. The event insertion and materialized shift/incident write are one transaction. A repeated same-user/site ID returns success without inserting again. Media has an independent immutable ID and retry receipt. The client persists the incident submission result before uploading each attachment. A media failure retains the bytes and allows subsequent submitted records to continue. Atomic SQLite state is separate from filesystem writes: a process crash can leave an orphan file, which an operator can reconcile against the media table.

Append-only events preserve capture and receipt times, location quality, handover acknowledgement and notes. Incident revisions retain approved content and prior generated draft text; transitions retain actor/time/note. Significant admin changes and summary approvals are audited. This is an audit trail, not a tamper-proof forensic ledger. Only the final selected audio recording is submitted; discarded rehearsal recordings are not server records.

## Patrols and summaries

Shift start is a single action and does not require handover acknowledgement. The guard remains on Home with start time, elapsed timer, and scheduled end, plus patrol, reporting, instructions and messaging actions. The most recently configured daily shift plan for the guard/site is snapshotted into the start event as `scheduled_end_at`, including overnight shifts. The browser clock calculates elapsed time from the persisted start timestamp, so reopening does not reset it. These shift times display in Africa/Lagos; missing plans are labeled explicitly. The fictional Bala demo gets a 06:00–18:00 schedule only if no plan is already configured. End-shift notes remain optional in the end-shift form, and earlier history is preserved.

Checkpoint QR labels contain random codes (readable codes for seeded examples). Camera scanning uses the browser's BarcodeDetector API where available; manual label entry is always available. Location is sampled only for start/end/scan actions, with permission denial and poor accuracy recorded for review. Device clock differences over a day are flagged. There is no background GPS or assertion that a scan proves security. QR codes can be copied; pilot supervision must interpret records accordingly.

Round IDs group checkpoints independently from scheduled time slots. Completing a round requires all current site checkpoints. The dashboard distinguishes scan count, started rounds and complete rounds. Schedules are simple daily plans rather than a recurring-calendar engine. Reporting dates are explicitly UTC; schedule labels are local site times. Historical daily counts currently use the site's current checkpoint and schedule configuration. Freeze those configurations during a pilot reporting period; effective-dated schedule/checkpoint snapshots and Africa/Lagos reporting boundaries are deployment follow-ups.

Daily counts come from SQL/event records, never model arithmetic. Source IDs are available as clickable record controls and in downloaded JSON. Narrative drafts use the AI adapter when configured, otherwise a deterministic template. Approval rejects stale counts if source activity has changed since draft creation. Approved summaries are immutable snapshots; later delayed records require a new draft and approval. There is no email customer delivery: approved summaries become visible in the owner's dashboard.

## Notifications

Guards can message assigned supervisors only after starting a shift. Messages require a shift and use the encrypted, idempotent event queue. Two-way conversations distinguish saved, submitted, seen and acknowledged. Owners cannot retrieve these private conversations or media; messages are excluded from customer summary sources.

Incident/urgent-alert events transactionally enqueue notifications for assigned supervisors. The supervisor home view polls while visible, and acknowledges receipt only after rendering. Failed receipt requests retry on subsequent polls. The UI separately shows submitted, delivered-to-app and acknowledged. Guard views can inspect their notification status. There is no SMS, WhatsApp, push or simulated external delivery adapter. This actual database inbox is the pilot adapter; future providers should implement durable jobs, provider receipt IDs, retry schedules and failure reporting.

## Shared device and offline constraints

Signing out clears decrypted state and keys from the active app and retains encrypted pending work. Reload starts locked. Each account has its own salt and encrypted vault. An offline sign-in is a local unlock of previously cached assignments, not renewed server authorization. Revoked assignments block sync after reconnection but cannot remotely erase an offline device. Password resets must first sync or recover the old vault with the old password; there is no recovery key or reset UI yet. Use strong individual passwords, OS screen lock and one active app tab per shared phone.

The vault encrypts the entire small pilot dataset, with media represented as base64. This favors simplicity over storage/memory efficiency; quota exhaustion is surfaced and does not claim a successful save. Synced media bytes are removed from the queue. Browser/OS eviction, cleared storage, lost passwords, or device loss can destroy unsynchronized work. Full native encrypted storage, managed-device remote wipe, dependable background transfer and stronger device attestation require a later native app/device-management effort.

## What is real, optional and still needed

Working locally: role enforcement; customer separation; shifts and handovers; patrols/QR sheets; audio/photo capture; text review and confirmation; private media; encrypted offline queue; retries; supervisor follow-up; administration; deterministic counts; approved summaries; in-app notifications; downloads.

Optional/unverified against paid service: live AI transcription and narrative generation. No API credential was provided; unavailable means unavailable. English only has been implemented, and real Nigerian English recordings still require evaluation. Pidgin and other languages are not advertised.

Before deployment: real contacts/accounts, HTTPS, backup/restore and monitoring, security review, effective-dated schedules, account revocation/recovery/admin tooling, media scanning/metadata policy, retention/deletion implementation, pagination for larger data, stronger rate limits across multiple processes, and real-device tests. Authentication has no MFA or password-reset service. Do not characterize this MVP as production-ready or legally compliant.


### Patrol schedules and reminders
Owners and supervisors can edit the selected site's daily patrol schedule from Overview > Scheduled rounds > Edit patrol schedule. Choose explicit HH:MM times or a repeating window (5–720 minutes; start inclusive, end exclusive). All times use Africa/Lagos, UTC+01:00; overnight windows are supported. Windows expand into the existing relational sites.schedule field, so no new migration is needed. Changes are scoped on the server and audited with old/new values. Connected guards refresh every 30 seconds on Home; offline guards use the last saved schedule.

The Home tile counts down to the earliest outstanding scheduled time since check-in or the last patrol start. Five minutes before, it shows an in-app reminder and tries vibration; at due time it changes color and counts elapsed overdue time. Starting a patrol creates an idempotent patrol_start event in the encrypted offline queue, with shift, guard, round, scheduled time, device capture and server receipt timestamps. Patrols follow the snapshotted shift schedule in order; a late start takes the earliest outstanding slot. Returning Home resumes an unfinished patrol. The server rejects skipped slots and starting another patrol before all checkpoints are recorded. Early starts remain enabled for testing and are marked as timing exceptions. A start is not a checkpoint scan or a completed round. Checkpoint-based completion counts remain unchanged.

Hear instructions > Enable patrol reminders requests optional notification permission. Notifications are generated locally while the page is visible, not by a background scheduler. No push service is configured. Vibration, notification permissions, silent mode, battery saver, locked screens and suspended browser tabs must be tested on actual Android devices. Keep the app open for this pilot. Reliable reminders while closed require a later push/native implementation. No delivery or supervisor acknowledgement is inferred from a phone reminder.


### Patrol selection, NFC and location review
Shift-start records snapshot patrol times and the planned end, keeping numbering stable (Patrol number X of Y). If no shift end is configured, the planning window is 24 hours from check-in. Changes to site patrol times apply to new shifts. Existing pre-snapshot demo shifts use the current site schedule. The server records early/late starts and unfinished slots at shift end for supervisor review. Early starts are intentionally still enabled for testing.

Guards select one unchecked checkpoint, choose QR or NFC, and a successful read automatically saves it with method, capture/receipt times and available GPS. A label must match the selected checkpoint. Manual label entry is a dialog behind Unable to scan and is recorded as a manual exception. There is no round picker or start-another-round shortcut. QR errors, denied permissions and unavailable NFC leave manual entry accessible.

NFC uses Web NFC NDEFReader with text records containing the checkpoint code printed on the QR sheet (for example OAK-1). Provision tags with an NFC writer before the pilot; raw card IDs, payment cards and access-control card protocols are not supported. This app does not write tags. Current implementation guidance: https://developer.chrome.com/docs/capabilities/nfc . Actual tag reads require compatible Android Chrome, NFC hardware enabled, HTTPS, an unlocked phone and user permission. The automated NFC test simulates the browser adapter; real tags still require device testing.

Migration 004 adds optional site reference coordinates and radius. Owners and supervisors configure these under Scheduled rounds > Location checks. Sign-in GPS is a one-time encrypted queued event; checkpoint GPS is attached to each scan. There is no watchPosition or background location tracking. Permission failures preserve a location-unavailable record. GPS checks compare distance with site radius and reported accuracy; accuracy worse than 100m is marked for review. No reference coordinates are invented for demo properties. Without a reference the app retains readings but does not claim proximity has been confirmed. GPS and QR/NFC reads are review evidence, not proof that a person is present or a property secure. Location details are kept off the guard entry and home screens. Browser location permission still applies; explain point-in-time collection during pilot onboarding.


### Simplified guard report flow
Guard subpages share Home beside the greeting. Reporting starts with Hold to speak and native audio playback. Typing expands under Type what happened and when. Submit itself approves the supplied recording/text; there is no additional checkbox. Voice-only submissions retain the original audio with an explicit listen-to-recording placeholder and an unknown-in-text event time; no transcript or event facts are fabricated when AI is unavailable. Configured AI can create a written draft for editing before Submit.

Take a photo uses getUserMedia with a visible camera preview, Capture photo and Cancel. It does not open a file chooser. Captured images are resized to at most 1600px wide and stored as JPEG in the encrypted draft. Choose a photo remains a library file input. Permission failure leaves the library option available. Camera streams stop on capture, cancellation or preview failure. Physical camera behavior still needs phone testing.

Recording supports a short tap to start/stop or a press-and-hold. The control shows microphone-opening status, recording state and elapsed duration, then saves a playable recording with its duration. A short release while requesting permission no longer silently appears to record; the status explains when the microphone is ready. The optional typed report is one observation box. Capture/submission and server receipt timestamps remain recorded automatically; unknown event time is not replaced with an invented exact incident time.

The recorder now uses native button clicks only (including keyboard activation): green Press to start, red Tap to stop, then saved-audio playback. Holding is no longer a separate gesture. Capture photo and Cancel share a two-column row in the camera dialog.

Start shift, final End shift and report Submit now require explicit confirmation. Cancelling keeps the current state and draft. Empty/photo-only drafts are rejected before the submit confirmation; either an audio recording or non-whitespace typed report is required. Photos remain optional, with the existing four-photo pilot limit.

Confirmations use styled modal HTML dialogs rather than browser confirm prompts. They provide a named alert dialog, focus trapping, Cancel/Escape dismissal, and side-by-side action buttons. End shift uses the muted red action color; Start shift and Submit use emerald. Background UI rendering pauses while a confirmation is open.

### Guard report history
The report page includes a collapsed Reports this shift section. It merges immutable server events with the current account’s encrypted pending queue by event ID, filtered to the current guard, site and shift. Entries open read-only pages with reporting timestamp, guard name, an always-visible read-only text box, and automatically loaded audio/photos. The text box stays empty for voice-only reports. Pending media uses local blob URLs, revoked on navigation; synchronized media loads through authorized expiring links. Missing remote attachments display a retry action rather than silently disappearing. Opening history preserves the draft. Guards have no report-edit/delete action; replaying an event ID is idempotent and does not overwrite it. No owner/supervisor deletion feature has been introduced.

Shift instructions: owners and supervisors publish reusable audio and/or typed instructions from the Shift instructions dashboard page. Publishing creates an audited version; a new shift snapshots the current version. Existing shifts retain their initial instructions. Recordings are private, authorized through site assignments and expiring session-bound links. Maximum 3 minutes recorded in-browser / 5 MB per upload, 100 MB instruction uploads per site. Old versions remain for history; offboarding must remove instruction_versions and their private files alongside existing records.

Guards download current and active-shift audio into their own encrypted vault during synchronization. Already downloaded recordings play offline. Uncached recordings need a connection; no speech synthesis or fabricated audio is used. Microphone permission denial falls back to typed instructions. Foreground patrol reminders remain automatic; mobile browsers do not guarantee vibration or notifications while backgrounded or locked. Test microphone capture, playback volume and offline replay on pilot Android devices.

Supervisor messages now reuse the incident voice/photo composer with a separate encrypted draft per shift. Guards can send voice or text plus up to four optional photos, during their shift. Message media is stored separately in message_media (migration 006), never as an incident; only the conversation’s guard and assigned supervisors can access it. Media downloads use authorized, expiring session-bound URLs. Attachment retries use existing stable IDs and the encrypted offline queue. The inbox displays audio players, pictures, and pending attachment state. Ordinary message receipt remains distinct from acknowledgement; these messages do not trigger external delivery or emergency dispatch. Offboarding must delete message_media files and records as well as messages. Photo/audio limits and the shared 1 GB site media quota apply.

Shift conversations (migration 007): each message has a relational message_context linking its guard and required shift for new records. Existing guard messages are backfilled by capture time. Assigned supervisors may send text, voice and photos to a guard's chosen shift, including archived shifts; a guard sees only their current active shift’s conversation records and media. Guards cannot browse previous-shift conversations; messaging is disabled on the off-duty home. Supervisor history remains available. Supervisors can select across assigned guards and shifts, or open a conversation from an inbox notification. Replies create in-app notifications for the guard. Seen status records a conversation being displayed, not proof audio was listened to. Foreground conversations refresh approximately every five seconds, updating the message list without replacing the composer or interrupting playback. No background delivery guarantee or external messaging service is implied.

Conversation drafts are separated by account (encrypted vault), site and shift; queued messages retain their shift identity across synchronization. Guard message lists filter cached records to the current shift. Synchronized media may need a connection to obtain private playback links. Offboarding must also remove message_context records. No chat deletion or message editing was added.


Shift-only messaging (migration 008): new message contexts require a shift. Guards cannot send messages captured before shift start or after shift end; valid offline captures may upload after the shift ends. Off-duty conversation generation and shortcuts have been removed. Existing unscoped legacy records remain stored for retention but are excluded from APIs, notifications, media access and chat lists. Old encrypted pending items are not discarded or reassigned to a shift; denied records no longer block later valid uploads.


Current-shift guard view: message and notification APIs restrict guard reads to an active shift, and private media links recheck that access when used. Supervisors retain historical access. Pending media captured during a completed shift can still upload, without reopening that conversation to the guard. Empty conversations stay hidden until a local or received message exists. Plain message rows show text/audio/photos, timestamp and sender name (You for the current user); supervisor names are included only on authorized message records.

Previous messages and unread indicator: the current-shift message list is newest first. The guard home tile shows a numeric new-message badge for unread incoming messages only. Opening the visible conversation marks those messages read locally in the encrypted vault; notification delivery receipts retry on reconnection. This indicates the conversation was opened, not that audio was listened to. Foreground home/message screens refresh about every five seconds. Historical shift conversations remain inaccessible to guards.

Session restoration: signing in stores a temporary vault unlock key and page selection in tab-scoped sessionStorage, bounded by the 12-hour session expiry. Refresh decrypts saved work, restores the page, and checks the server session when connected. Offline refresh uses the saved account until expiry. No password is stored. Explicit sign-out removes the key and invalidates restored sibling tabs via a shared epoch; pending work remains encrypted. Browser session recovery may retain tab storage, so shared-phone users must explicitly sign out. This convenience does not protect an unlocked tab from someone using the phone or from same-origin script compromise. A new independent tab requires sign-in. Existing users must sign in once after installing this update.
